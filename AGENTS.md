# AGENTS.md: guide for AI agents and contributors

NoteCraft is an open-source, native, **1:1 replacement for Microsoft OneNote** (the Microsoft 365
desktop app for Windows in its current, 2024 look: decision D1 in `docs/plan.md`) written in **Rust only** (no
JavaScript or TypeScript). **No Tauri, Electron or webview shells:** the desktop app is native
egui/eframe on wgpu, and the web build is the same Rust compiled to WebAssembly (trunk +
wasm-bindgen). The product name is always written **NoteCraft** (`{Function}Craft`, like its
siblings PhotoCraft, WordCraft, GridCraft, DeckCraft, PdfCraft…) in user-facing text; machine
names stay lowercase: crates (`notecraft-*`), binaries, file names, ids
(`ai.storyteller.notecraft`). Standards and learnings shared across the Crafting Apps live in
`../craftrules` (not public: ask a maintainer for the standards relevant to your change);
contribute reusable learnings there, never code. Shared Rust components live in
[storytold/craft-libs](https://github.com/storytold/craft-libs) and are pinned by immutable git
revision. The goal is **1:1 OneNote parity** — the same layout, ribbon, menus, commands,
shortcuts, behaviour and file compatibility — and every feature drivable by agents. Read this
file first, then `docs/`.

## 2. Workspace map

```text
crates/
  util geom color ink-geom   L0 foundation (geometry in page points, colours, ink geometry)
  codecs                     L0 standalone codecs (no workspace deps)
  doc                        L1 document model: notebook → section group → section → page → outlines (pure data)
  text ink search math       L2 rich-text editing, ink, full-text search, math
  render gpu format          L3 CPU reference renderer (the oracle), wgpu renderer, native .ncraft format
  onestore import-export ... L4 .one/.onetoc2/.onepkg ([MS-ONESTORE]/[MS-ONE]), other formats, OCR hook, plug-ins, sync
  engine                     L5 Session + command registry (every action is a command)
  ui-egui automation         L6 egui shell (ribbon, panes, dialogs); control channel + MCP
apps/
  notecraft                  desktop app (eframe/wgpu), TCP control server
  notecraft-cli              headless CLI (run/batch/commands/mcp)
  notecraft-web              the same app in the browser (trunk + wasm-bindgen)
xtask/                       cargo xtask layers | wasm | ci | assets | parity | deny | version
```

Crates appear when they get their first code; the layer of every planned crate is already
registered in `xtask/src/layers.rs`. **Layering is enforced** by `cargo xtask layers`: a crate may
depend only on lower layers; nothing below `ui-egui` may use egui, eframe, winit, rfd or arboard.

## 3. Golden rules

### Never crash (outranks feature work)

People trust NoteCraft with their notes, and a crash loses them. A malformed `.one` file, a bad
command or MCP param, a corrupt settings file, an odd keystroke or a full disk must produce an
error the user or agent can act on, never a panic. Shared standard:
`../craftrules/standards/never-crash.md`.

- **Non-test code never panics.** No `unwrap()`, `expect()`, `panic!`, `unreachable!`, `todo!` or
  `unimplemented!`. Return the crate's error type and propagate with `?`. Unfinished features
  return an "unsupported" error or stay disabled in the UI.
- **No `unsafe`.** The workspace sets `unsafe_code = "forbid"`.
- **Input-derived numbers are hostile.** `get()` instead of `[i]`, slice strings only at char
  boundaries, `checked_*`/`saturating_*` for sizes and offsets, guard division and NaN casts, cap
  allocations sized by input, bound recursion (documents can be deep or cyclic).
- **Last-resort guard.** `Session::run` catches an escaped panic, restores the page and reports an
  error. It's a safety net, not a licence. Keep `panic = "unwind"`.
- **Prove it.** Every crash fix lands with a regression test that panicked before the fix. The
  `panic_hunt` test runs every command with adversarial params and must stay green.
- **Enforced by clippy.** `clippy.toml` allows `unwrap`/`expect`/`panic`/indexing in tests only;
  every crate root carries
  `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::unimplemented, clippy::todo, clippy::unreachable)]`.

### The parity mandate

1. **Catalog first.** Every user-visible thing NoteCraft does corresponds to a row of
   `docs/parity-catalog.md`. Pick work from the catalog (highest priority first), implement it to
   behavioural parity, test it, flip its status, run `cargo xtask parity`, commit.
2. **Everything is a command.** New user-visible behaviour = a `CommandSpec` in
   `crates/engine/src/<area>_cmds.rs` with id, **parity-catalog id**, label, **menu path mirroring
   OneNote's ribbon/menu path** (`Home/Tags/To Do Tag`), OneNote's shortcut, params doc, `enabled`
   predicate and a `run` that records **exactly one undo step**, plus tests. The ribbon, context
   menus, shortcuts, CLI, control channel and MCP all dispatch by id.
3. **No fake UI.** A control that does nothing is drawn **disabled** (its tooltip says why) and
   its catalog row is `disabled`. Never mark a row `wired` without a test, nor `verified` without
   a test carrying `// parity: <ID>` that pins the documented behaviour.
4. **Never claim parity you have not measured.** Undocumented behaviour is implemented the most
   plausible way and marked `unverified` in the catalog's Notes and in `docs/parity.md`.

### Clean room

- We study OneNote **only** through public documentation (Microsoft support/learn pages, the
  public Open Specifications [MS-ONESTORE], [MS-ONE], [MS-ONETOC2], [MS-FSSHTTPB], [MS-CAB], the
  Office Fluent UI control-identifier lists) and user-visible behaviour. Never decompile,
  disassemble or read anything inside a Microsoft binary; never copy Microsoft code, strings
  beyond functional labels ("Bold", "Insert Table"), templates or sample notebooks.
- **Assets: absolutely no Microsoft iconography or images.** Every icon is drawn in code by us
  (`crates/ui-egui/src/icons.rs`) or permissively licensed with its licence beside it and a row in
  `ATTRIBUTION.md` (`cargo xtask assets` fails otherwise). No OneNote logos or branding; the name
  "OneNote" appears only to describe compatibility.
- **Fonts** never go in this repo: they live in
  [storytold/craft-fonts](https://github.com/storytold/craft-fonts), an optional build input
  (`CRAFT_FONTS_DIR`).
- Parsers cite the spec section beside each structure, field and validation rule
  (`// [MS-ONESTORE] §2.4.3 FileNodeListFragment`), and every bounds check says which hostile input
  it stops. Test fixtures are synthetic (generated by our own writer) or permissively licensed.
- Never copy GPL/LGPL/AGPL code; dependencies are permissive only (`deny.toml`).

### Other rules

- **The UI is thin and data-driven.** UI state lives in `ui-egui` and is serializable so the
  control channel can read and drive it; colours come from `theme::Tokens`.
- **Verify UI changes visually** with the offscreen screenshot example (`egui_kittest`, no window,
  no focus stealing) and look at the PNG.
- **Never break wasm.** L0–L6 must `cargo check --target wasm32-unknown-unknown`
  (`cargo xtask wasm`). File-system code is `cfg(not(target_arch = "wasm32"))` or goes through the
  platform services; never call `Instant::now`/`SystemTime::now` on wasm (clippy denies them).
- **Local-first and private.** No telemetry, no network access by default.
- **Comments explain why**: invariants, units and coordinate spaces, ownership, trade-offs. Every
  public item has `///` docs; every crate has `//!` docs saying its layer and why it sits there.

## 4. Before you finish a task

```sh
cargo fmt --all
cargo clippy -p <crates> --all-targets -- -D warnings
cargo test -p <crates you touched>
cargo xtask layers
cargo xtask wasm            # if you touched L0–L6
cargo xtask parity          # if you added commands or changed catalog rows; commit the regenerated docs
cargo xtask ci              # the full gate (fmt, clippy, tests, assets, layers, wasm, parity --check, deny)
```

Then append a terse entry to `log/devlog.md` (what landed, numbers, what's still open). Sessions
can end abruptly, so the dev log plus a green tree is how the next agent picks up.

## 5. Git

- Small, coherent, buildable commits; only commit green code. Subject `Area: what changed`
  (≤72 chars), milestone id where one applies (`M1 Engine: command registry and undo`), a body
  that says why. Never `--no-verify`, never force-push, never rewrite published history.
- Feature branches merged into `main`; finished milestones are tagged (`m1-core`, …) in the same
  commit as their devlog entry. Never commit corpora, proprietary files, secrets or `target*/`.

## 6. Parallel agents

- Use your own target dir (`CARGO_TARGET_DIR=target/agent-<name>`) and your own branch/worktree;
  edit only the files you own. Shared files (`engine/src/lib.rs`, the registry list in
  `engine/src/commands.rs`, `ui-egui/src/lib.rs`) get small, surgical edits.
- Put new commands in a **new module** (`engine/src/<area>_cmds.rs` with a `specs()` function).
- Keep every `Cargo.toml` valid at all times (the `crates/*` glob means one broken manifest breaks
  everyone): write manifests to a temp file outside `crates/`, then `mv` them into place.
- Disk space: delete `target/agent-*` dirs of finished agents.
